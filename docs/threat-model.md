# Threat model (draft, P1)

Asset: the master private key on the token (it never leaves it) and the plaintext of what is unwrapped. The service holds neither the key nor, at rest, any plaintext; it holds the PIN in memory while unlocked.
Rule one: **a compromised client can do exactly what its policy allows and no more, and every use is written down.**

| Attacker | Can | Mitigation | Residual |
|---|---|---|---|
| Compromised client (stolen client key) | `wrap`/`unwrap` what its policy allows, at its rate limit | deny by default; per client+key ops, context rules, rate and size limits; audit of allowed and refused; revoke by config reload; short-lived certs | until revoked it can unwrap what policy lets it; limit bounds the speed of bulk decryption |
| Network attacker | observe, replay, impersonate the server | TLS 1.3 with mandatory client cert; service terminates TLS itself, believes no header; server cert pinned by clients | TLS stack bugs |
| Unauthenticated peer | connect, probe | handshake fails before any handler; `/healthz` and `status` touch no card; no oracle for unauthenticated | handshake-level DoS |
| Stolen token, no PIN | try PINs | card blocks after 3 tries; service tries the PIN once and stays `locked` after a refusal | physical attacks on the card |
| Stolen PIN, no token | nothing | token is required for any private operation | — |
| Host compromise (root on the service host) | read PIN from memory, drive the token while it is unlocked, forge audit | PIN only in memory, `unlock` over admin socket; systemd sandboxing; audit hash chain, shipped off-host; spare token and rotation limit the window | root on an unlocked host is full use of the token for the time it is unlocked; not defended |
| Operator error | wrong key, wrong context, lost card | named keys with state; `rewrap`; multi-recipient format (spare card); written recovery procedure | lost sole card = lost data |
| Client exhausting the token | many ECDH operations | per-client and per-key rate limits, global budget, `busy` with `retryable` | shared global budget lets one client starve others unless per-client limits are set |
| Malicious ciphertext | off-curve ephemeral point, oversize body | point validated before the token is asked; size limits; fuzz targets for parsers | token-side bugs |
| Wrapped text moved to another context | open a DEK sealed for tenant A in tenant B | context map canonicalised into AEAD additional data; policy restricts contexts | policy must be written correctly |
| KMS-JSON face: client with a stolen signing secret | everything its grants allow, from its allowed addresses | the client also needs its certificate (unless `no_cert`); `allow_from` is judged by the TCP peer address, never a header; secrets of 20 bytes or more (32 for `no_cert`), read from files of mode 0600, replaced by reload; every call is in the audit | with `no_cert` the secret is the **only** proof: a leak plus an address on the list is full use of that client's rights (sealing, signing and MAC keys it is granted, never `derive`: with `no_cert` a leak lets the thief sign or make MACs from a listed address until the secret is replaced; the limits per minute bound the speed, the audit holds the digest prefix of what was signed); behind a proxy or NAT the address list is as wide as the proxy |
| KMS-JSON face: peer without a certificate | send requests, guess secrets | only credentials marked `no_cert` are accepted without a certificate; refused signatures are counted by address and block that address for a minute after 20; the signature verifier, the blob and the bodies are fuzzed | the TLS handshake and the parsers are reachable without a certificate when any client has `no_cert`; no replay cache (TLS protects the capture; a front that logs requests could replay within 5 minutes); `/v1/sys/health` of the Transit face is static and answers anyone; every refused request is one audit line (with fixed names: the path and operation of a peer that nobody knows are logged as `unknown`), so a flood is a flood of short lines |
| KMS-JSON face: two names on one private key | a client that may derive on one name computes what is sealed, signed or authenticated under the other, and the MAC key of a derived-key MAC | with the face in use the configuration refuses two keys on one private key (same file, same module/token/CKA_ID, one pinned fingerprint), and the service compares the public keys when the tokens answer, at start and at reload; blobs bind the key name and version into the AEAD | a copy of a key on a token that is not present at start is seen only at the next reload (pin the fingerprint to see it at once) |
| KMS-JSON face: `derive` | a client that may derive can open anything sealed to that key | `derive` only on `key_agreement` keys in fixed mode, dedicated to it; a key has one usage, so sealing keys with contexts are not exposed to it | whoever may derive on a key opens everything sealed to it, with no context check |
| Reader of the metrics | learns when secrets are opened, the rate of refusals, whether the token is locked or absent, the load on the token | off by default; on the admin socket only (mode 0600); `basic` detail counts by face and outcome class; no client, key or address as a label; bounded series | whoever scrapes sees activity patterns: give the dashboards the access of the audit log; a published exporter without authentication would leak the same (the exposed-exporter findings of 2024) |
| KMS-JSON face: MAC key | the MAC key is derived on the token and used by the service, so it is in memory while it works (and for `mac_cache_seconds`) | derived from the token's key with a point of unknown logarithm; not stored; the token key is dedicated to it; the cache is off by default | host memory reveals the MAC key (not the token key) for the time it is there |
| KMS-JSON face: the service seals | sees the plaintext while it seals or opens (as the Transit face) | not logged; the audit holds the key, client and context only; plaintext wiped after use | memory of the host while the request runs |

## Attack surface (reviewed for release 0.4.0)

| Entry | Who can reach it | Parsers and checks | Notes |
|---|---|---|---|
| The listener (TLS 1.3, one port): the Transit face (`/v1/…`), the KMS-JSON face (`/` with a target header), the gRPC face (`application/grpc`, the token endpoint), the REST face (`/keys`, `/rng`, the token endpoint of the tenant) | any peer that completes a TLS handshake; the client certificate is checked per request, and a call without one needs a credential marked `no_cert` from a listed address | strict parsers with size limits, fuzzed (Transit request, KMS-JSON request, ecies text, SigV4, configuration); the key must exist, be on the face and be granted; one answer for "no such key" and "not allowed" | the faces share one policy, one gate to the token and one audit log |
| The token endpoints (gRPC face, REST face) | any peer | form body limited to 16 KiB; RS256 JWT only; refused credentials counted by address | access tokens are random, in memory, one hour |
| The admin socket (unix, mode 0600) | local users with the right to the socket | unlock the token, status, metrics | not on the network |
| The PKCS#11 module and the token | the service only | ECDH point validated before the token sees it; a finite gate to the token | a malicious module is out of scope |
| The configuration and the secret files | the operator | checked at start and at reload (all or nothing); owner and mode of secret files | a reload cannot change the listener or the enabled faces |
| The supply chain | build and release | pinned actions and base images, Dependabot, Dependency Review, govulncheck, signed releases with provenance and SBOM ([verifying-releases.md](verifying-releases.md)) | the release is built by one workflow |

Critical code paths: the policy check, the audit write before the answer, the opening of a sealed text (`internal/kmsops`, `internal/scheme/ecies`, `internal/keyops`), and the authentication of the faces (`internal/oauth`, `internal/sigv4`, `internal/authn`); each is covered by tests and, for parsers, by fuzz targets.

Out of scope: availability of the token fleet, side channels inside the token, a malicious vendor PKCS#11 module.
